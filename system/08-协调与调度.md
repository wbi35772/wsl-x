# 08 · 协调与调度

跨应用的启动顺序、依赖、重启策略与定时任务。单应用参数见对应 `app/<slug>` 分支。

## 1. 启动链

```text
Windows 登录
  └─ 计划任务 wsl-hosts-sync（登录后 15 秒，最高权限）→ 更新 hosts 的 wsl.x01
       └─ WSL2 轻量 VM（所有发行版共享，systemd）
            ├─ mihomo-uidrule.service（oneshot：给 uid 994 加 ip rule）
            ├─ mihomo.service（always，3 秒重启）
            │    ├─ DNS 127.0.0.1:53（fake-ip 198.18.0.0/16）
            │    ├─ mixed :7890（HTTP/SOCKS5）
            │    ├─ API/UI 127.0.0.1:9090
            │    └─ TUN x01tun0
            ├─ docker-tun-bypass（ip rule 100：docker0 → main）
            └─ docker.service
                 └─ dockerd 清理陈旧 sandbox 3–4 分钟
                      └─ 按 restart policy 拉起容器
                           └─ goofish-healthy（/health 200）
```

关键点：

- **mihomo 必须先起**。WSL 的 DNS 指向 `127.0.0.1:53`；mihomo 未起时域名解析全挂，拉镜像/访问订阅都会失败。IP 直连不受影响。
- **`vmIdleTimeout=86400000` 必须保留**。默认 60 秒空闲会关整台 VM，容器跟着“假重启”，冷启动还要再等 dockerd 3–4 分钟。
- **Windows 不能用 `127.0.0.1:端口`**。`localhostForwarding=false`；统一走 `http://wsl.x01:<port>`。

## 2. 重启策略

| 单元 | 策略 | 手动 `docker stop` 后 | `wsl --shutdown` 后 | 说明 |
|---|---|---|---|---|
| `goofish-hardware-sniper` | unless-stopped | 不自动回 | 自动回 | 唯一常驻应用 |
| `x01-data-postgres` | unless-stopped | 不自动回 | 自动回 | 恢复窗口约 4 分钟 |
| `x01-data-mongo` | unless-stopped | 不自动回 | 自动回 | — |
| `x01-dev-forgejo` / `-db` | unless-stopped | 不自动回 | 自动回 | 两容器同起同停 |
| `x01-sec-mobsf` | unless-stopped | 不自动回 | 自动回 | — |
| `x01-sec-mitmproxy` | unless-stopped | 不自动回 | 自动回 | — |
| `x01-ops-portainer` | unless-stopped | 不自动回 | 自动回 | 停止时退出码 2 属正常 |
| `x01-net-substore` | `no` | 不起 | 不起 | 已弃用 |
| `clash-proxy-demo` | `no` | 不起 | 不起 | 实验，host 网络 |
| `shardx-team` | 未设置 | 不起 | 不起 | 按需手动 |
| `net-egress` | unless-stopped | 不自动回 | 自动回 | — |
| `mihomo` | systemd `always` | — | 自动起 | 3 秒重启 |

语义：`unless-stopped` 只保证“非手动停止”的容器随 Docker 启动；手动 `docker stop` 的不会自动回来。

## 3. 依赖顺序

推荐顺序（有依赖才需要严格）：

1. `mihomo`（DNS/出口）
2. `docker-tun-bypass`（容器出网）
3. `data/postgres`、`data/mongo`
4. `dev/forgejo`（MySQL 由 compose 一起拉起）
5. `sec/mobsf`、`sec/mitmproxy`（相互独立）
6. `ops/portainer`
7. 应用：`goofish-hardware-sniper`、`shardx-team`、`net-egress`

批量拉起当前 x01 服务：

```bash
for m in data/postgres data/mongo dev/forgejo sec/mobsf sec/mitmproxy ops/portainer; do
  docker compose -f ~/infra/$m/compose.yaml up -d
done
```

应用依赖：

- `goofish` 需要 DNS；掉登录时需要 Windows Chrome CDP `9223`（`scripts/start_chrome_debug.ps1`）。
- `net-egress` 只绑 `127.0.0.1`，供 WSL 内使用。
- `shardx-team` 依赖数据卷 `shardx-team-data`。

## 4. 定时与后台任务

| 任务 | 状态 | 说明 |
|---|---|---|
| `mihomo-refresh.timer` | disabled（2026-10-29） | 节点不再自动刷新；手动 `sudo -u mihomo ./bin/refresh-providers` |
| Sub-Store 同步 cron | `0 0 31 2 *` | 永不触发；Sub-Store 已弃用 |
| goofish 内置调度 | 运行 | 7 个启用任务，分钟偏移 `1–7`，抖动 0–180 秒 |
| goofish 失败保护 | 运行 | 连续 3 次失败暂停 24 小时 |
| goofish AI 并发 | 1 | `AI_ANALYSIS_CONCURRENCY=1`，每次详情最多 6 个 |
| `wsl-hosts-sync` | 登录后 15 秒 | 更新 hosts；IP 变了靠它同步 |
| `mihomo-uidrule.service` | 每次启动 | 防止 mihomo 自身出站被 TUN 回环 |

调度原则：

- 同一分钟不开多个浏览器任务；任务分钟错开，避免内存峰值。
- 免费模型限流时保持并发 1；先规则预过滤，再送 AI。
- 订阅刷新、批量抓取不要与 `wsl --shutdown`/冷启动重叠。

## 5. 端口分配

| 段 | 端口 | 绑定 | 归属 |
|---|---|---|---|
| 系统 | `53`、`7890`、`9090`、`2375` | `127.0.0.1` / `*` | mihomo、Docker API |
| 数据 | `5432`、`27017` | `127.0.0.1` | Postgres、Mongo |
| 开发 | `3005`、`222` | `0.0.0.0` | Forgejo HTTP/SSH |
| 安全 | `8000`；`8080`、`8081` | `0.0.0.0` | MobSF；mitmproxy / mitmweb |
| 运维 | `9443` | `0.0.0.0` | Portainer |
| 应用 | `8086`、`8787` | `0.0.0.0` | goofish、shardx-team |
| 出网 | `7891`、`9099` | `127.0.0.1` | net-egress |
| 实验 | `8085`、`7900`、`9093`、`10001+` | host | clash-proxy-demo |

规则：

- 数据/出网类只绑 `127.0.0.1`；UI 类才绑 `0.0.0.0`。
- host 网络只用于实验；`clash-proxy-demo` 与 mihomo 不要同时占同名端口。
- 新应用先查本表；端口冲突写进对应 `app/<slug>` 分支的 `meta.yaml`。

## 6. 故障与恢复窗口

| 场景 | 预期 | 处置 |
|---|---|---|
| 冷启动慢 | dockerd 清理 3–4 分钟 | 等待；不要反复 `wsl --shutdown` |
| Postgres 强停后拒绝连接 | 约 4 分钟恢复 | 等 `pg_isready` 通过 |
| DNS 全挂 | 域名解析失败 | 临时把 `/etc/resolv.conf` 改成 `172.30.192.1` |
| 容器不能上网 | `ip rule` 缺 100 规则 | `sudo systemctl restart docker-tun-bypass` |
| Windows 打不开 | `localhostForwarding=false` | 用 `wsl.x01` 或跑 `wslip.cmd` |
| Forgejo ROOT_URL 不对 | 页面资源 404 | 用 `http://wsl.x01:3005/` 访问 |

## 7. 变更流程

1. 在对应 `app/<slug>` 分支改应用的记录/配置。
2. 在 WSL 实测（`x01 up/down`、健康检查）。
3. 端口、路径、依赖有变化 → 同步改 `main` 的 `system/03`、`system/08`、`apps/README.md`。
4. 故障与新结论追加到 `system/07-历史与故障处置.md` 的时间线。
